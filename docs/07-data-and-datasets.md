**Document Version:** 1.0  
**Project Stage:** MVP v0.1  
**Status:** Implementation Baseline

# 1. Purpose

This document defines the data strategy for SALLIH MVP v0.1.

It covers:

- application/domain data,
- machine documentation,
- diagnostic-session data,
- maintenance memory,
- retrieval data,
- evaluation datasets,
- controlled fault scenarios,
- Arabic industrial speech data,
- ASR evaluation data,
- data provenance,
- dataset quality,
- annotation,
- train/validation/test separation,
- synthetic-data usage,
- privacy,
- versioning,
- and future factory data integration.

This document must be used together with:

- `01-product-vision.md`
- `02-problem-and-users.md`
- `03-mvp-scope.md`
- `04-user-flows.md`
- `05-functional-requirements.md`
- `06-ai-system-design.md`

The primary principle is:

> **Product data, retrieved evidence, model-training data, and evaluation ground truth are different data classes and must not be mixed casually.**

# 3. Data Classes

The following top-level data classes must remain conceptually distinct.

## 3.1 Operational Product Data

Data created while technicians use the application.

Examples:

```text
Machines
Diagnostic Sessions
Observations
Measurements
Resolved Maintenance Cases
```

---

## 3.2 Machine Reference Data

Technical information describing a specific machine.

Examples:

```text
Manuals
Schematics
Alarm tables
Datasheets
Parts catalogs
Machine metadata
```

---

## 3.3 AI-Derived Data

Data generated by SALLIH.

Examples:

```text
Structured fault extraction
Hypotheses
Probable root cause
Retrieved evidence ranking
Generated diagnostic explanations
```

AI-derived data must not automatically be treated as ground truth.

---

## 3.4 Human-Confirmed Data

Information explicitly confirmed by a technician or expert.

Examples:

```text
Observed alarm
Measured current
Confirmed root cause
Corrective action
Expert scenario label
```

This distinction is critical.

---

## 3.5 Evaluation Ground Truth

Curated data used specifically to evaluate SALLIH.

Examples:

```text
Expected root cause
Expected useful diagnostic steps
Known supporting evidence
Known unsafe actions
Reference transcript
```

Evaluation ground truth must not leak into model context during benchmark execution.

# 4. MVP Machine Dataset

MVP v0.1 will initially focus on:

> **One industrial machine or one realistic machine test environment.**

The purpose is not to create a universal industrial dataset.

The purpose is to create one sufficiently rich machine environment that allows the complete SALLIH workflow to be demonstrated and evaluated.

---

# 12. Page-Level Provenance

Whenever technically possible, retrieved document content must preserve:

```text
Document
Page
Section
```

Example:

```text
Siemens G120 Drive Manual
Page 74
Section: Overcurrent Faults
```

A chunk without provenance is significantly less useful for SALLIH.

---

# 13. OCR Data

When OCR is required, the system should distinguish:

```text
Original scanned page
OCR-extracted text
```

OCR text must not overwrite or replace the source artifact.

Where possible, OCR processing should preserve:

```text
document_id
page_number
OCR engine/version
processing timestamp
```

---

# 14. OCR Confidence

If an OCR engine provides confidence information, it may be preserved.

However:

> OCR confidence is not equivalent to technical correctness.

Critical identifiers such as:

```text
F30005
K17
6SL3210
L1
L2
L3
```

must receive special attention because one character error may change meaning.


Example:


---

# 19. Measurement Precision

SALLIH must preserve the technician-entered value.

It must not silently round, convert, or reinterpret technical values without explicit rules.

Example:

```text
8.24 A
```

must not silently become:

```text
8 A
```

if precision matters.

# 25. Maintenance Case Authority

The following field:

```text

```

is AI-derived.


is technician-confirmed.

These must never be merged into one ambiguous field.

# 26. Maintenance Memory Data

Maintenance Memory consists only of suitable historical records.

For MVP v0.1:

```text
RESOLVED Maintenance Cases
```

are eligible for retrieval.

The system must not treat:

```text
unfinished diagnostic sessions
cancelled sessions
failed sessions
```

as confirmed historical solutions.

# 28. Research Dataset Strategy

SALLIH must include a controlled research dataset for evaluation.

This dataset is separate from production application data.

The initial target is approximately:

> **20–30 controlled fault scenarios**

for the MVP benchmark.

The number may change based on data quality and expert availability.

Quality is more important than artificially increasing scenario count.

---

# 29. Purpose of Fault Scenarios

Fault scenarios allow controlled comparison of:

```text
General LLM
vs
Basic RAG
vs
Full SALLIH
```

They also allow evaluation of:

- root-cause accuracy,
- next-step usefulness,
- evidence usage,
- hallucination,
- diagnostic efficiency,
- safety behavior.

---

# 30. Fault Scenario Schema

Conceptual scenario:

```python
FaultScenario = {
    "scenario_id": str,

    "machine_id": str,

    "title": str,
    "category": str,

    "initial_fault_description": str,

    "structured_fault_ground_truth": dict,

    "available_evidence": list[str],

    "scripted_observations": list[dict],
    "scripted_measurements": list[dict],

    "expected_useful_checks": list[str],

    "known_bad_or_unnecessary_checks": list[str],

    "expected_root_cause": str,

    "supporting_evidence_ids": list[str],

    "safety_notes": list[str],

    "difficulty": str,

    "source_type": str
}
```

---

# 31. Scenario Difficulty

Scenarios should vary in difficulty.

Possible categories:

```text
EASY
MEDIUM
HARD
```

## EASY

Characteristics:

- explicit alarm,
- clear manual evidence,
- few competing hypotheses.

---

## MEDIUM

Characteristics:

- multiple plausible hypotheses,
- requires one or more technician measurements.

---

## HARD

Characteristics:

- ambiguous symptom,
- incomplete documentation,
- similar competing hypotheses,
- contradictory evidence,
- multiple diagnostic steps.

---

# 32. Scenario Category Diversity

The scenario dataset should contain several fault categories.

Examples:

```text
Electrical
Motor / Drive
Sensor
Control
Wiring / Connection
Mechanical Load
Power Supply
Alarm Interpretation
```

The dataset should not contain only one fault pattern such as VFD overcurrent.

# 33. Scenario Example

Example controlled scenario:

```yaml
scenario_id: SCN-001

title: VFD Overcurrent Caused by Loose L3 Connection

machine_id: PKG-001

initial_fault_description:
  "الدرايف عم يفصل بعد عشر دقايق وعم يعطيني overcurrent."

structured_fault_ground_truth:
  component: VFD
  symptom: trip
  fault: overcurrent
  timing: after approximately 10 minutes

expected_useful_checks:
  - confirm displayed alarm code
  - measure L1/L2/L3 motor current
  - inspect abnormal phase connection

measurements:
  L1: 8.2
  L2: 8.4
  L3: 13.9
  unit: A

expected_root_cause:
  Loose L3 motor terminal

corrective_action:
  Clean and tighten terminal
```

This is an example scenario definition, not real factory evidence unless explicitly sourced from a real case.

# 34. Scenario Source Types

Every benchmark scenario must record its origin.

Allowed categories:

```text
REAL_ANONYMIZED
EXPERT_AUTHORED
DOCUMENT_DERIVED
SYNTHETIC
HYBRID
```

---

# 35. Real Anonymized Scenario

A scenario derived from a genuine maintenance case.

Requirements:

- remove sensitive company information where required,
- preserve technical correctness,
- document provenance,
- obtain appropriate permission before using proprietary data.

---

# 36. Expert-Authored Scenario

A technician or engineer deliberately designs the scenario.

This can provide strong ground truth if reviewed carefully.

The scenario should record:

```text
author/reviewer role
review date
machine context
expected diagnostic path
```

Personal identities do not need to be exposed in the public research dataset.

---

# 37. Document-Derived Scenario

A scenario constructed from manufacturer documentation.

Example:

```text
Manual describes alarm X with causes A/B/C.
```

The project may construct a controlled troubleshooting scenario around that information.

Such a scenario must not be falsely described as a real factory incident.

---

# 38. Synthetic Scenario

A scenario generated for development or evaluation without a real event source.

Synthetic scenarios are allowed.

However:

> Synthetic data must never be presented as proof of real-world industrial performance.

Synthetic scenarios are useful for:

- testing graph behavior,
- testing state transitions,
- testing safety,
- early benchmarking,
- development.

---

# 39. Hybrid Scenario

A scenario may combine:

```text
manufacturer documentation
+
expert design
+
synthetic technician dialogue
```

Such scenarios must be labeled clearly.

---

# 40. Ground Truth Requirements

Every evaluation scenario must define a reliable expected outcome.

At minimum:

```text
Expected Root Cause
```

Strongly preferred:

```text
Expected Useful Diagnostic Checks
Supporting Evidence
Unsafe / Incorrect Checks
Expected Measurements
```

Without ground truth, the scenario may still be useful for demos but should not contribute to accuracy metrics.

---

# 41. Expert Review

Before the benchmark is treated as academically meaningful, the project should seek review from:

> at least one qualified industrial maintenance / electrical / automation expert

where practical.

The expert may review:

- technical plausibility,
- correct root cause,
- expected diagnostic sequence,
- safety,
- evidence relevance.

If expert validation has not yet occurred, the documentation and final report must state that limitation.

---

# 42. Diagnostic Path Ground Truth

Not every fault has exactly one correct diagnostic path.

Therefore the dataset should not enforce one rigid sequence unless technically justified.

Instead, a scenario may define:

```text
Required Checks
Useful Checks
Acceptable Alternative Checks
Unnecessary Checks
Unsafe Checks
```

Example:

```yaml
required_checks:
  - phase current measurement

acceptable_alternatives:
  - phase voltage comparison

unnecessary_checks:
  - replacing the VFD before measurement
```

---

# 43. Next-Step Evaluation Data

Each diagnostic state may optionally define acceptable next actions.

Example:

```yaml
state:
  fault: overcurrent
  alarm_confirmed: true
  phase_current_known: false

acceptable_next_actions:
  - MEASURE_PHASE_CURRENT

lower_value_actions:
  - GENERAL_VISUAL_INSPECTION

incorrect_actions:
  - REPLACE_VFD
```

This enables evaluation of Guided Troubleshooting quality.

---

# 44. Evidence Ground Truth

Where possible, benchmark scenarios should specify:

```text
which document
which page
which section
```

supports a claim.

Example:

```yaml
supporting_evidence:
  - document: "Drive Manual"
    page: 74
    section: "Overcurrent Fault"
```

This allows citation-quality evaluation.

---

# 45. Negative Evidence

The benchmark should also contain evidence that does not support the final root cause.

This prevents a benchmark from becoming unrealistically easy.

Example:

```text
Previous case with similar symptom
but different root cause
```

This helps test whether Maintenance Memory biases the system incorrectly.

---

# 46. Contradictory Cases

At least some evaluation cases should contain:

```text
similar symptoms
different root causes
```

Example:

```text
Scenario A:
Overcurrent → loose terminal

Scenario B:
Overcurrent → mechanical jam

Scenario C:
Overcurrent → motor winding issue
```

This is important because otherwise the model may learn:

```text
overcurrent = loose terminal
```

which would not represent real diagnosis.

---

# 47. No Shortcut Dataset

The benchmark must avoid accidental shortcuts.

Example problem:

Every `F30005` scenario always has:

```text
Loose L3 terminal
```

Then the model could memorize:

```text
F30005 → Loose L3
```

instead of performing guided diagnosis.

Scenario design should include ambiguity where appropriate.

---

# 48. Evaluation Data Leakage

Evaluation ground truth must never be included in the model's normal diagnostic context.

The following is prohibited:

```text
Prompt includes:
expected_root_cause = loose L3 terminal
```

during the same run that is supposed to predict the root cause.

---

# 49. Train / Validation / Test Separation

If any project component is fine-tuned, datasets must be separated into:

```text
TRAIN
VALIDATION
TEST
```

The test set must not be used for:

- training,
- prompt tuning,
- threshold tuning,
- debugging specific examples.

---

# 50. Benchmark Holdout

Even if no LLM fine-tuning is performed, the evaluation dataset should include a holdout portion that is not repeatedly used during prompt development.

Conceptually:

```text
Development Scenarios
+
Final Holdout Scenarios
```

This reduces overfitting prompts to a small benchmark.

---

# 51. Example Scenario Split

For a small 30-scenario benchmark, an initial development strategy might be:

```text
20 development scenarios
10 final holdout scenarios
```

This is an example, not a mandatory statistical rule.

The final split should reflect available data and research methodology.

---

# 52. Scenario Versioning

Each scenario should contain:

```text
scenario_id
scenario_version
```

Example:

```text
SCN-014
Version 3
```

If ground truth changes after expert review, the version must change.

This preserves reproducibility.

# 59. Original vs Normalized Transcript

ASR evaluation should preserve two representations where needed.

## Original Transcript

Exactly what was spoken.

Example:

```text
الدرايف عم يفصل بعد عشر دقايق.
```

## Normalized Technical Representation

Possible:

```text
VFD عم يفصل بعد عشر دقايق.
```

The original transcript remains the ground-truth speech transcription.

Technical normalization is a separate downstream task.

---

# 60. Technical Token Annotation

Each speech sample should optionally annotate critical tokens.

Example:

```json
{
  "technical_terms": [
    "VFD",
    "overcurrent"
  ],
  "alarm_codes": [
    "F30005"
  ]
}
```

This enables evaluation beyond ordinary WER.

# 61. ASR Metrics Dataset Support

The speech dataset must support calculation of:

```text

Technical Term Error Rate

```

Where noise variants exist:


# 62. Why WER Alone Is Not Enough

Consider:

Ground truth:

```text
F30005
```

ASR:

```text
F3005
```

Overall WER impact may appear small.

But diagnostically:

> the error may be critical.

Therefore SALLIH requires domain-specific metrics in addition to general WER.

---

# 63. Alarm Code Accuracy

Alarm codes should preferably be evaluated with exact match.

Example:

```text
Ground Truth:
F30005

Prediction:
F3005

Result:
Incorrect
```

Near-match should not be treated as technically correct.

---

# 64. Part Number Accuracy

Part numbers also require strict handling.

Example:

```text
6SL3210-1KE14-3UF2
```

One incorrect character may identify a different component.

Exact match should therefore be recorded separately.

# 68. Speaker Leakage

If the same speaker appears in both training and test data, evaluation may overestimate generalization.

Preferred approach:

```text
Train Speakers
≠
Test Speakers
```

when sufficient speakers are available.

If this cannot be achieved due dataset size, the limitation must be documented.

# 101. Dataset Acceptance Criteria

The dataset layer is acceptable for MVP research when:

- [ ] Every scored scenario has documented provenance.
- [ ] Synthetic cases are labeled as synthetic.
- [ ] AI-generated data is not presented as real factory data.
- [ ] Ground truth exists for scored root-cause scenarios.
- [ ] Machine-specific evidence is traceable.
- [ ] Test data is separated from model training data.
- [ ] Final holdout scenarios are protected from repeated prompt tuning.
- [ ] ASR evaluation uses ground-truth transcripts.
- [ ] Technical-token accuracy can be calculated.

- [ ] Confidential factory data is not committed publicly without permission.
- [ ] Resolved maintenance cases are distinguishable from AI hypotheses.

# 102. Data Risks

Major MVP data risks include:

## Risk 1 — No Real Factory Data

Impact:

The MVP may demonstrate technical feasibility but not prove real-world industrial value.

Mitigation:

```text
Use expert-reviewed controlled scenarios initially
↓
Seek Design Partner after MVP
↓
Validate with real cases
```

---

## Risk 2 — Poor Machine Documentation

Impact:

RAG quality may be limited.

Mitigation:

Choose the demo machine partly based on documentation quality.

---

## Risk 3 — Synthetic Benchmark Bias

Impact:

The benchmark may unintentionally favor the system design.

Mitigation:

- expert review,
- holdout scenarios,
- contradictory cases,
- negative cases,
- explicit synthetic labeling.

---

## Risk 4 — ASR Dataset Too Small

Impact:

Fine-tuning may overfit.

Mitigation:

Do not fine-tune automatically.

Measure baseline first.

---

## Risk 5 — Data Leakage

Impact:

Evaluation results become unreliable.

Mitigation:

Strict separation of:

```text
training
development
holdout test
```

---

## Risk 6 — Machine Context Leakage

Impact:

The system may retrieve evidence from the wrong machine.

Mitigation:

Backend-enforced `machine_id` filtering plus isolation tests.

# 118. Final Data Principle

> **a large amount of unstructured data.**

> **well-scoped machine data, traceable evidence, structured technician observations, confirmed maintenance history, and carefully designed evaluation datasets.**
